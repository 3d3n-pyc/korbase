# Migrations

**Use this when** you need to change a database [schema](glossary.md#schema) to match your models, one reviewed SQL file at a time.

## The idea

The schema is the shape of the database: its tables, columns, keys and indexes. When you change a model, for example by adding a field, the real database must change too. A [migration](glossary.md#migration) is a SQL file that makes one such change, like `0002_add_note.sql`. Files are numbered, so they run in order.

Why files, and not "sync the database to the models" on start-up? Because a schema change can destroy data. A file is something you can read before it runs, review in a pull request, and keep in git next to the code that needs it. Every database (your laptop, staging, production) then gets the same changes in the same order.

Once a file has been applied somewhere, never edit it. Other databases already ran the old text, and they would no longer match. To change the schema again, write a new file.

## The workflow

Four steps: `make`, review, `apply`, `status`.

1. `make` compares your models with the `public` schema of the database and writes the SQL that closes the gap, as the next numbered file.
2. You read the file. Dangerous statements carry a [`-- korbase:review`](glossary.md#review-marker) marker.
3. `apply` runs the pending files in order and records each one.
4. `status` lists every file as `applied`, `pending`, `changed` or `missing`.

Here are two rounds. `models.py` holds one model:

```python
from typing import Annotated, Optional

import msgspec

from korbase import PK, table


@table("items")
class Item(msgspec.Struct):
    id: Annotated[int, PK()]
    name: str
    note: Optional[str] = None
```

```sh
export KORBASE_DSN="postgresql://user:password@localhost:5432/app"
python -m korbase.migrate make --models models --dir migrations -m "create items"
python -m korbase.migrate apply --dir migrations
python -m korbase.migrate status --dir migrations
```

The output is `migrations/0001_create_items.sql`, then `applied 0001_create_items.sql` twice (once from `apply`, once from `status`). Now rename the field `name` to `title` and run `make` again. The new file stops `apply`:

```sql
-- Generated by korbase on 2026-11-20.
SET standard_conforming_strings = on;
-- korbase:review NOT NULL column without default fails on a non-empty table
-- possible rename: rewrite as ALTER TABLE "items" RENAME COLUMN "name" TO "title"
ALTER TABLE "items" ADD COLUMN "title" text NOT NULL;
-- korbase:review drops column items.name, its data is lost
-- possible rename: rewrite as ALTER TABLE "items" RENAME COLUMN "name" TO "title"
ALTER TABLE "items" DROP COLUMN "name";
```

`apply` prints `error: migration 0002_rename_name_to_title.sql still has a -- korbase:review marker` and runs nothing. korbase cannot know that this was a rename. You do, so you edit the file to keep the data:

```sql
-- Generated by korbase on 2026-11-20.
SET standard_conforming_strings = on;
ALTER TABLE "items" RENAME COLUMN "name" TO "title";
```

Now `apply` runs it, and a new `make` prints `no changes`.

## Command line

- `--models` is the dotted path of a module that holds your `@table` classes. It must be importable from the current directory. `make` needs it.
- `--dir` is the migrations folder. It defaults to `migrations`.
- `-m` names the new file. It defaults to `migration`.
- `make` prints the new file's path, or `no changes`. `apply` prints one `applied NAME` line per file. `status` prints `STATE NAME` per file.
- The exit code is 0 on success and 1 on error.

## Python API

```python
import asyncio
import os

from korbase import Database
from korbase.migrate import apply, collect_models, make, status


async def migrate(dsn: str) -> None:
    async with await Database.connect(dsn) as db:
        path = await make(db, collect_models("models"), "migrations", "create items")
        print(path)  # the new file's path, or None when nothing differs
        print(await status(db, "migrations"))  # [("0001_create_items.sql", "pending")]
        print(await apply(db, "migrations"))  # ["0001_create_items.sql"]


asyncio.run(migrate(os.environ["KORBASE_DSN"]))
```

- `collect_models(module_path)` returns the `@table` classes of a module. It raises `KorbaseError` if there are none.
- `make(db, models, directory, message)` returns the new file's path, or `None`.
- `apply(db, directory)` returns the names of the files it ran.
- `status(db, directory)` returns a list of `(name, state)` pairs.

## Reviewing a file

A statement that can lose data or fail on existing rows gets a `-- korbase:review` line above it. `apply` refuses to run while any pending file still contains one. It applies nothing, not even the files before it. To go on:

1. Read the statement and check it against your data.
2. Change the SQL if it is wrong.
3. Delete the `-- korbase:review` lines.

Then run `apply` again. If a file fails half way, its changes are rolled back and the error names the file. Files before it stay applied. Fix the file or the database, then run `apply` again.

## Tests

`create_all(db, models)` creates the tables of your models straight from the models, in one [transaction](glossary.md#transaction). It records no versions and runs no files. Use it to set up an empty test database. Use `make` and `apply` for every database that holds data you keep.

```python
from korbase import Database
from korbase.migrate import collect_models, create_all


async def setup(db: Database) -> None:
    await create_all(db, collect_models("models"))
```

The tests of this workflow are in `tests/test_migrate.py` and `tests/test_apply.py`.

## Going further

**How `make` works.** It does not change your data. In one transaction it creates a [scratch schema](glossary.md#scratch-schema), builds your models in it, reads that schema and `public`, writes the difference, and always [rolls back](glossary.md#rollback). So it needs the `CREATE` privilege on the database. Run it against a development database, not production. It compares with `public`: use the database whose schema should be brought up to date.

**What the differ detects.** Tables created or dropped. Columns added or dropped, and changes of type, `NOT NULL`, default and identity. Primary keys, unique constraints, foreign keys (with `ON DELETE`) and indexes. Renames are not detected.

**Ordering.** Statements are sorted so they can run. First: create tables, add columns, alter columns, change keys, add foreign keys, add indexes. Then the drops: foreign keys, indexes and constraints, columns, and tables last. A foreign key held up by a primary key change is dropped first and added back. Identical statements appear once.

**Tables korbase does not manage.** Any table in `public` that is not in your models is a drop, flagged for review. An index that is not in your models is dropped the same way. Point `make` at a shared database and you will see other tools' tables as drops. Delete those lines, or use a database of your own. The `korbase_migrations` table is left out. Only ordinary and partitioned tables are read: views and other objects are not.

**Review markers, and why each exists.**

| Marker reason | Why |
| --- | --- |
| drops table, drops column | the data is lost |
| type changes | the `USING` cast can fail, or change values |
| becomes `NOT NULL` | fails if a `NULL` exists |
| new `NOT NULL` column without default | fails on a table that has rows |
| identity changes | the values that the database hands out change |
| primary key changes | other tables may depend on it |
| index not managed or removed | it may serve queries that korbase cannot see |

**Rename hints.** When a column is dropped and another added in the same table, `make` adds `-- possible rename: rewrite as ALTER TABLE ... RENAME COLUMN ...`. Dropped and added columns are paired in order, so with several at once, check each pair. Replace the `ADD COLUMN` and `DROP COLUMN` with the `RENAME COLUMN`. If the column was indexed, the `DROP INDEX` and `CREATE INDEX` lines can stay, but their review lines go.

**Checksums and the version table.** `apply` creates the [version table](glossary.md#version-table) `korbase_migrations`: the name, the [checksum](glossary.md#checksum) (SHA-256 of the file bytes) and the time of each applied file. `status` compares files with rows:

- `pending`: not applied yet.
- `applied`: applied, and the file is unchanged.
- `changed`: applied, but the checksum differs now.
- `missing`: applied, but the file is gone.

`apply` refuses, and runs nothing, if any file is `changed` or `missing`. If you edited an applied file by mistake, put the original text back. File names must look like `0001_create_items.sql`: four or more digits, an underscore, then lower-case letters, digits and underscores. A pending file numbered lower than the last applied one is refused, because it would run out of order.

**Advisory lock.** `apply` takes a Postgres [advisory lock](glossary.md#advisory-lock) on one connection for the whole run, before it reads the version table. Two runs at the same time therefore apply each file once: the second waits, then finds nothing to do. The lock is released even when a file fails.

**`-- korbase:no-transaction` and `CREATE INDEX CONCURRENTLY`.** Each file normally runs in its own transaction, with its version row. Postgres refuses `CREATE INDEX CONCURRENTLY` inside a transaction. Make the first line of the file `-- korbase:no-transaction` to run it without one:

```sql
-- korbase:no-transaction
CREATE INDEX CONCURRENTLY "items_title_idx" ON "items" ("title");
```

The marker must be the very first line, so move it above the header that `make` writes, or delete the header. Put one statement in such a file. A file is sent as one multi-statement text, and Postgres treats that as one transaction, so a second statement next to `CONCURRENTLY` fails with `cannot run inside a transaction block`. Without a transaction, a failed file is not rolled back, so check the database by hand.

**`standard_conforming_strings` is forced on.** `apply` sets it to `on` for its own session, whatever the role's default, then restores it. A backslash in a string literal is therefore read the same way in every file. `make` writes `SET standard_conforming_strings = on;` at the top of its files for the same reason.

**`KORBASE_DSN` and `--dsn`.** Set `KORBASE_DSN` in the environment. `--dsn` wins when both are given, but a command-line argument shows in `ps` and in shell history, so other users on the machine can read it. Errors never print the DSN: a connection failure reads `could not connect to the database`.
